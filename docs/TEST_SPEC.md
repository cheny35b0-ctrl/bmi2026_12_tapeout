# テスト仕様書 — 各テストベンチが何を検証しているか

このファイルは `tb/` 以下のテストベンチが **何をどこまで保証しているか** の一覧です。
「テストが通った」がどういう意味なのかを、TB のソースを読まずに把握できるようにするのが目的です。

- 最終更新: 2026-08-01
- 対象ブランチ: `akagi/add_test_for_sending_circuit`

---

## 1. 実行方法

```sh
./scripts/run_tests.sh
```

`tb/filelists/*_filelist.txt` にある全テストベンチをコンパイル・実行します。
1 つでも失敗すると非ゼロ終了するので、そのまま CI から呼べます。所要時間は全部で約 10 秒。

個別に走らせる場合:

```sh
iverilog -o sim/SELECT_tb.vvp -c tb/filelists/SELECT_tb_filelist.txt
cd sim && vvp SELECT_tb.vvp
```

### 合否の見方

セルフチェック付きの TB は、各検証項目を `[PASS]` / `[FAIL]` で出力し、最後にサマリを出します。
失敗が 1 件でもあれば `$fatal` で異常終了します（`$finish` だと終了コードが 0 になり
CI が誤って PASS と判定するため）。ハングした場合もウォッチドッグが `$fatal` で落とします。

> `BMI_testbench_single.v` は自動判定を持ちません。VCD を目視するための TB であり、
> 「PASS」と表示されてもシミュレーションが最後まで走ったことしか意味しません。

### 期待値の作り方（重要）

符号化データの期待値は、**RTL のコピーではなく仕様から独立に書いた参照モデル**
（`golden_encode()`）で計算しています。

- 仕様: 拘束長 K=3、符号化率 1/2、生成多項式 G0=7(111) / G1=5(101)、MSB first、ゼロ終端
- RTL (`CONV_ENCODER.v`) は `bit_counter` 駆動の逐次実装、参照モデルは単純な for ループ実装で、
  構造がまったく違う → 実装のバグが期待値にコピーされない

シリアル出力の検証も同様に、`OUT` を `comcon_out` の値をインデックスにして並べ直し、
**TB が与えた ADDRESS / TYPE / DATA と突き合わせて**います。
ビット位置の定数を適当に合わせただけでは通りません。

## 3. `CONV_ENCODER_TB.v` — 畳み込み符号化器 単体

**対象**: `rtl/comm/CONV_ENCODER.v`（+ `rtl/common/counter_8bit.v`）

### 全ケース共通の検証項目

| # | 検証内容 |
|---|---|
| C1 | `ENCODE_DONE` が返ってくる（ハングしない） |
| C2 | 64bit 符号化結果が参照モデルと一致する |
| C3 | ゼロ終端した入力で内部状態が `2'b00` に戻る |
| C4 | `START` から `ENCODE_DONE` までのレイテンシが 34〜35 clk に収まる |

> **34/35 の 2 通りを許容している理由**: POR 直後の初回だけ 35clk になります。
> `counter_rst` が POR で 1 にセットされているため、start が発火したクロックでは
> ビットカウンタがまだ進まず 1clk ぶんずれます。2 回目以降は 34clk で一定です。
> どちらも正常動作であり、バグではありません。

### テストケース一覧

| ケース | 入力 | 追加の検証項目 |
|---|---|---|
| POR 直後 | — | `DATA_OUT`=0 / `ENCODE_DONE`=0 |
| Case 1 | `32'h00000000` | 全 0 入力の符号化結果が全 0 |
| Case 2 | `32'h3FFFFFFC`（全 1 + ゼロ終端） | 共通 4 項目 |
| Case 3 | `32'hAAAAAAA8`（1010… 交互） | 共通 4 項目 |
| Case 4 | `32'h55555554`（0101… 交互） | 共通 4 項目 |
| Case 5 | `32'h80000000`（MSB のみ 1） | インパルス応答が `6'b11_01_11` / 3 シンボルで収束 |
| Case 6 | `32'h12345678` | 共通 4 項目 |
| Case 7 | `32'hDEADBEEC` | 共通 4 項目 |
| Case 8 | 実フレーム相当（ADDR=0x2C, TYPE=11, DATA=0x7B3A9） | `COM_CON_TOP` が渡すのと同じビット並びで検証 |
| レイテンシ予算 | — | 符号化が `state=counter` の期間（約 68clk）内に完了する |
| Case 9 | `32'hFFFFFFFF`（**契約違反**） | 符号化結果自体は一致するが、内部状態は 00 に戻らない |
| 完了後の保持 | `32'h12345678` | `START` を落としても `DATA_OUT` が保持される |
| 連続実行 | `32'hDEADBEEC` × 2 回 | 同じ入力で同じ結果 / レイテンシがぶれない |
| 符号化中の POR | `32'hDEADBEEC` | POR で `DATA_OUT` / `ENCODE_DONE` / 内部状態がクリアされ、解除後に再び正常動作する |

### この TB が押さえている「使い方の契約」

- **`START` はレベル信号**。符号化中はずっと High に保つ必要があります。1clk パルスにすると
  ビットカウンタが 0 に固定され、`ENCODE_DONE` が永久に立ちません
  （`counter_rst || START == 1'b0` がカウンタ RST のため）。
- **入力の下位 2bit は 0（ゼロ終端）にすること**。そうしないと内部状態が 00 に戻らず、
  次のフレームに影響します。Case 9 がこの契約を明示的に確認しています。

## 6. `TOP_202512TO_tb.v` — システム結合

**対象**: `rtl/top/TOP_202512TO.v` 全体（マンチェスター受信 → コマンド解釈 → 刺激/測定 → シリアル送信）

### テスト環境

- **コマンド送信**: `ORDER` をマンチェスター符号化（`MAN = CLK ^~ ORDER`）して 350bit のフル設定コマンドと、
  20bit の短コマンド（起動トリガ）を実際に送り込みます。
- **ADC コードの注入**: `ADC_logic` は SAR 型で phase 4〜13 の間に 1bit ずつ確定させるため、
  TB 側で phase に応じた `COMPARATOR` を返して**任意の 10bit 変換結果を作れる**ようにしています。
  これで「コンパレータ → ADC → DATA → シリアル出力」まで一気通貫で検証できます。
  - 電気側: `10'b10_0110_1011` / 光側: `10'b01_1100_0101`
- **自機アドレス**: `unique_debug=1`, `unique_low=2'b00` → `8'h2C`

### 周回一覧

| 周 | 目的 | 符号化 | データ源 | 主な設定 |
|---|---|---|---|---|
| 1 | 測定 + 符号化 ON（外部パッド `ENCODE_ENABLE_ext`） | ON | ADC 実測値 | 測定 ON / 刺激 OFF |
| 2 | 1 周目と同じコマンドを再送（**回帰**: 前回値で `com=10` 打ち切りが起きないか） | ON | ADC 実測値 | 同上 |
| 3 | 設定値を変更して再送（PERIOD/WIDTH を変更）+ **非符号化パス** | OFF | ADC 実測値 | 測定 ON |
| 4 | 刺激 ON / 測定 OFF | — | — | 電気刺激 P/N + 光刺激 |
| 5 | 刺激をもう一度起動（**回帰**: `msec_count` 持ち越しで DELAY がずれないか） | — | — | 同上 |
| 6 | 符号化 ON を **`command[343]` 経由**で（外部パッドは OFF） | ON | デバッグ固定値 | 測定 ON |
| 7 | **他デバイス宛て**（`0x2D`）コマンドの拒否 | — | — | — |
| 8 | 刺激パルスの**定量検証** | — | — | PERIOD=3ms / WIDTH=1ms / LOOP=3 / DELAY=1ms / N 極 OFF |

### コマンド受信の検証項目（各周共通）

| # | 検証内容 |
|---|---|
| 1 | 350bit 全部が書き込まれた（`COMMAND.com ≥ 350`） |
| 2 | 送信後に standby へ復帰した |
| 3 | 宛先アドレスで受理された |
| 4 | 起動ビット `bit10` は 0（フル設定コマンドでは起動しない） |
| 5 | イネーブル部 `bit[17:10]` が一致 |
| 6 | 電気刺激 P の PERIOD が一致 |
| 7 | 電気刺激 P の WIDTH が一致 |

### 短コマンド（起動トリガ）の検証項目

| # | 検証内容 |
|---|---|
| 1 | General Address `0xFF` で受理された |
| 2 | 起動ビット `bit10` が立った |
| 3 | **イネーブル設定 `bit[17:11]` が保持されている**（短コマンドで設定が壊れない） |

### 測定モード（1・2・3・6 周目）の検証項目

| # | 検証内容 |
|---|---|
| 1 | 電気測定が期待回数（3 回）走った |
| 2 | 光測定が期待回数（3 回）走った |

### シリアル出力フレームの検証項目（1・2・3・6 周目）

| # | 検証内容 |
|---|---|
| 1 | 測定後にシリアルフレームが送出された |
| 2 | **電気測定 ADC が注入コードどおりに変換した** |
| 3 | **光測定 ADC が注入コードどおりに変換した** |

### 刺激モード（4・5 周目）の検証項目

| # | 検証内容 |
|---|---|
| 1 | 電気刺激 P が発火した |
| 2 | 電気刺激 N が発火した |
| 3 | 光刺激が出力された |
| 4 | 電気測定は動いていない（モード排他） |
| 5 | 光測定は動いていない |
| 6 | 電気刺激 P の DELAY が設定値（1ms）どおり |

### アドレス不一致（7 周目）の検証項目

| # | 検証内容 |
|---|---|
| 1 | 他デバイス宛てコマンドの後も standby へ戻っている |
| 2 | パラメータ領域 `command[399:20]` が書き換わらない |
| 3 | アドレス不一致で書き込みが途中で打ち切られた（`com < 350`） |

> `COMMAND.v` はアドレス 8bit を受け切った時点（`com ≥ 8`）で不一致を判定して中断するため、
> 先頭バイトは書き込まれますがパラメータ領域は変化しません。

### 刺激パルスの定量検証（8 周目）の検証項目

| # | 検証内容 |
|---|---|
| 1 | 電気刺激 P のパルス幅が WIDTH どおり（実測 999900ns / 設定 1ms、許容 −1clk） |
| 2 | 電気刺激 P の周期が PERIOD どおり（実測 2999900ns / 設定 3ms、許容 −1clk） |
| 3 | 電気刺激 P の発火回数が LOOP どおり（3 回） |
| 4 | N 極 `OPERATE=0` のとき N 極は発火しない |

> **実測が設定値ちょうど −1clk になる理由**: `STIM.v` は state が `on` へ遷移してから
> `STIM` を立てるため、1 発目の立ち上がりだけが msec カウンタの刻みより 1clk 遅れます。
> 2 発目以降は純粋にカウンタ駆動なので、1 発目起点で測る幅と周期はどちらも 1clk ぶん短く出ます。

## 7. 検証していないこと（既知のカバレッジ穴）

テストが通っても**保証されていない**項目です。

| # | 未検証の項目 | 影響 |
|---|---|---|
| 1 | **`ADDRESS[5:0]` の境界値（62 / 63）** | `ADDRESS[5:0]=63` で**送信が始まらない既知の不具合**あり（下記） |
| 2 | `counter_8bit` の折返しタイミング（±1clk） | `ADC_logic` の `counter_5us`(PERIOD=15) の周期が 1clk ずれても検出できない |
| 3 | 光刺激の定量（幅・周期・回数） | 「出力された」ことしか見ていない。定量検証は電気刺激 P のみ |
| 4 | 電気刺激 N の定量（幅・周期・回数） | 「発火した / しない」しか見ていない |
| 5 | `offset_calib` / `CAL1` / `CAL2` / `S1` / `S3` | 一切検証していない |
| 6 | `MAN_DECODER` の異常系（ビット化け、途中断、ノイズ） | 正常系のみ |
| 7 | `COMMAND.v` の中断条件の網羅 | アドレス不一致のみ確認。他の中断パスは未確認 |
| 8 | `CLK_OUT` / `ORDER_OUT`（デコーダ出力パッド） | 未検証 |
| 9 | 複数デバイスの同時接続シナリオ | 単体デバイスのみ |

### 既知の不具合: `ADDRESS[5:0] = 63` で送信が止まる

`rtl/common/counter_8bit.v:21` の折返し条件が `COUNT + 1 < PERIOD` のため、
`PERIOD=63` の `delay_counter`（`rtl/comm/COM_ENABLE.v:94`）は **0〜62 までしか数えません**。
その結果 `DELAY == address_delay`（`COM_ENABLE.v:73`）が永久に成立せず、
`delay` 状態から抜けられなくなります。

実測（`COM_CON_OUT` 単体）:

```
DELAY=61 : 送信開始 OK (12205 clk 後)
DELAY=62 : 送信開始 OK (12405 clk 後)
DELAY=63 : 送信が始まらない (COM_ENABLE.state = delay のまま)
```

**現状の `TOP_202512TO.v` では踏みません。** `unique[5:0]` は `unique_debug` により
0〜3（debug=0）か 44〜47（debug=1）にしかならないためです（`TOP_202512TO.v:63-65`）。
将来アドレス割り当てを変更する場合の制約として記録しておきます。

## 8. 付録: テスト自体の実効性（変異テスト結果）

「テストが通る」ことと「テストがバグを見つけられる」ことは別なので、
RTL に意図的なバグを 1 箇所ずつ注入し、テストが落ちるかを確認しました。

**結果: 20 件中 18 件を検出（検出率 90%）**

| 注入したバグ | 検出した TB |
|---|---|
| 生成多項式 G1 を壊す | CONV_ENCODER / COM_CON_OUT / TOP |
| c0/c1 の出力順を入替 | CONV_ENCODER / COM_CON_OUT / TOP |
| シフトレジスタの状態更新を止める | CONV_ENCODER / COM_CON_OUT / TOP |
| 入力ビット順を LSB first に | CONV_ENCODER / COM_CON_OUT / TOP |
| 符号化完了を 1clk 早める | CONV_ENCODER / COM_CON_OUT / TOP |
| SELECT の状態遷移閾値 42→43 | SELECT / COM_CON_OUT / TOP |
| SELECT の状態遷移閾値 98→97 | SELECT / COM_CON_OUT / TOP |
| ストップビットを 0 に | SELECT / COM_CON_OUT / TOP |
| ADDRESS のシフト方向を逆に | SELECT / COM_CON_OUT / TOP |
| `ENCODE_ENABLE` を無視 | SELECT / COM_CON_OUT / TOP |
| `ADC_STATE` での中断を削除 | SELECT |
| 符号化器の入力 TYPE 順を入替 | COM_CON_OUT |
| 符号化器の START 状態を誤らせる | COM_CON_OUT / TOP |
| 符号化 ON/OFF のデータ選択を反転 | COM_CON_OUT / TOP |
| デバッグ固定データを変える | COM_CON_OUT / TOP |
| `DATA_OPT`/`DATA_ELE` の連結順を入替 | COM_CON_OUT / TOP |
| TYPE エンコードを誤らせる | COM_CON_OUT |
| `SHIFT_REG` のロード状態を誤らせる | COM_CON_OUT / TOP |
| `counter_8bit` の折返し条件を `<=` に | **検出できず**（→ 7章の穴 #1, #2） |
| `SHIFT_REG` の `ENCODE_DONE` 待ちを外す | **検出できず**（等価変異・下記） |

> **`ENCODE_DONE` 待ちを外しても落ちない理由**: `counter` 状態は約 68clk あるのに対し
> 符号化は 34clk で終わるため、待たなくても `counter` 状態の最後にロードされる値は
> 結局正しくなります。挙動が変わらない「等価変異」であり、テストの穴ではありません。
